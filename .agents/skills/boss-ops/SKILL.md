# Boss 筛选值守与运维

本仓库的筛选进程是长时本机任务（单轮可持续数小时）。通过 `--watch` 将后台浏览器进程与前台事件值守解耦，实现零轮询消耗盯完全程。

## 值守循环

1. **启动或续守**：
   - 续守当前轮或首次启动：`uv run python src/boss_screen/__main__.py --watch`（不设短超时）。
   - 上轮已结束、显式开启新一轮：`uv run python src/boss_screen/__main__.py --watch --start`。
   - 进程在跑时从本轮 `流式筛选开始` 起回看日志并挂接，不会漏掉挂接空档内的暂停或结束记录；进程已退出且已有历史日志时，`--watch` 只报告上轮结果，不自动开新一轮。
2. **按返回码处置**：
   - **退出码 `0`（`值守结束：完成`）**：仅当日志记录 `筛选结果：完成` 且无未解除告警时返回 `0`。查询 `boss.db` 统计本轮各 `stage` 数量及新增 `ai_keep` 岗位并汇报。
   - **退出码 `2`（告警或非完成退出）**：按下方「现场排障」处置；人工恢复后再次执行 `--watch` 续守，直至退出码为 `0`。

完成标准：`--watch` 以退出码 `0` 跑完所有城市与关键词并输出统计汇报，或定位到需人工介入的阻塞点并附现场信息通知用户。

## 现场排障

筛选进程使用 Patchright 管理本机有头 Chrome，不开启 `9222` 调试端口，也不挂载第二个 CDP 客户端（避免额外 `Runtime.enable`）。排障只读检查 `screen.log`、`boss.db`，并由用户在原 Chrome 窗口操作。

- **`自动恢复中` / `暂停自恢复 n/5`（瞬时接口或页面读取故障）**
  - 无需操作或重挂 `--watch`。单次请求失败若 3 秒内没有同类成功响应，也会进入恢复；不同接口的成功不会掩盖它。运行器每隔 25 秒重载目标页，最多 5 次，最后一次仍留出响应等待时间，再决定是否报 `暂停等人`。
  - 成功统一输出 `目标业务已恢复，继续`，`--watch` 继续值守。若只恢复了列表、原岗位正文仍缺失，该岗保留 `jd_queued`，停因写明“下轮再取”，同轮不重复点击，继续处理后续岗位。
- **`暂停等人`（验证、登录、恢复预算耗尽或不可自动恢复的故障）**
  1. 查看 `screen.log` 末尾的暂停原因及处置提示。Boss 风控码会连同服务器原文写出，例如 `岗位接口业务码 35（您的IP地址存在异常行为.）`。
  2. **人机验证或登录（自动确认恢复）**：原窗口出现验证后运行器停止自动重载，避免打断验证。用户完成验证或登录，让页面回到当前目标搜索页或重新点开当前目标岗位；新的成功业务响应到达后输出 `目标业务已恢复，继续`，随后执行 `--watch` 续守。
  3. **风控码 35（IP 级）**：请更换可用出口（必要时用 Clash 全局模式绕开 `GEOIP,CN,DIRECT`），在原窗口硬刷新确认业务恢复，再发送 `kill -USR1 $(cat .boss-screen.lock)` 放行；或 `kill -INT $(cat .boss-screen.lock)` 结束本轮等待冷却。
  4. **其余需显式放行的异常**：用户确认原窗口目标列表或详情已恢复正常后，发送 `kill -USR1 $(cat .boss-screen.lock)`；日志出现 `目标业务已恢复，继续` 后执行 `--watch` 续守。疑似账号限流或封控时，直接 `kill -INT $(cat .boss-screen.lock)` 结束本轮。
- **`停止本轮筛选` / `筛选结果：熔断`（进程已收尾退出）**
  - **AI 熔断**（标题初筛、详情 JD、启动补评共用计数），日志会写明是哪一类：
    - **确定性失败**（如 401/403/404 等配置或鉴权类）连续 3 次即停——重试不会自愈，先核对 `boss.yaml` 的 `ai.baseUrl` / `ai.apiKey` / `ai.model`。
    - **可重试失败**（429、5xx、超时、回复不合契约）按最近 12 次调用计：样本 ≥ 8 且失败率 ≥ 75% 才停，说明上游持续不可用；偶发 429 会被运行时的退避重试吸收（最多 4 次尝试，429 按网关 `reset_seconds` 冷却，单次封顶 20 秒），不再误伤整轮。
    恢复后用 `--watch --start` 开启新一轮（库内已抓正文的待评记录会在启动时零网页点击优先补评）。
  - **`onRisk: stop` 触发停机**：先根据日志原因确认是否为验证或接口限制，再决定是否用 `--watch --start` 重开。
- **`值守告警`（日志连续 300 秒无更新）**
  1. 检查 `.boss-screen.lock` 对应 PID 是否存活，并请用户查看 Chrome 窗口状态。
  2. 需停止时发送 `kill -INT $(cat .boss-screen.lock)`，等待日志写出 `筛选结果：人工停止` 并释放锁；确认需重开时用 `--watch --start`。

## 调优与回拨重评

- **增量只来自查询维度**：Boss 每个搜索词最多 20 页 × 15 张（300 条后 `hasMore` 即 false），列表接口 `joblist.json` 是 POST 且没有任何排序参数，页面也只有「推荐」。加深滚动拿不到更多岗位，要增量就加词（`Python`、`后端`、`算法` 这类泛词）或加城市。2026-10-21 实测：`Agent` 300 张里只有 15 个库里没有的新岗，`Python` 300 张里有 163 个。

用户修改 `boss.yaml`（关键词、黑名单、规则词、候选人画像或 Prompt）后：

1. **抽检停因**：`boss.db` 为 WAL 模式，可在运行期直接并发查询各 `stage` 的 `company, job, reason` 复盘误杀或漏杀。
2. **回拨状态（仅使用 `src/boss_screen/rules.py` 中 `PLACED_STAGES` 定义的合法值）**：
   - **零点击重评 JD**：对已有正文的记录（`trim(jd) != ''`），将 `stage` 更新为 `'ai_jd_pending'`。下次启动时 `_retry_pending_jds()` 会在打开网页前直接后台重评。
   - **重评标题初筛**：将无正文的被淘汰/含糊记录 `stage` 更新为 `'ai_title_pending'`，下次列表刷到时重新调用标题 AI。
3. **重启生效**：`boss.yaml` 在启动时加载。若筛选进程在跑，执行 `kill -INT $(cat .boss-screen.lock)` 等待收尾退出，再执行 `--watch --start` 启动新配置。

完成标准：`boss.db` 目标记录已更新为合法待评状态，且新配置已通过重启筛选进程生效。
